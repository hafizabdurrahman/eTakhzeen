3. DESIGN SYSTEM — HOW ETAKHZEEN SHOULD LOOK AND FEEL
-------------------------------------------------------
Brand feeling: eTakhzeen should feel like the storefront of a real,
established company — calm, trustworthy, organized, and slightly premium.
Think "established regional retailer with a modern web presence," not
"weekend hackathon project" and not "flashy startup with neon gradients."
Prioritize clarity and hierarchy over decoration. Every screen should look
like it was designed by the same person.

3.1 Color palette
  - Primary brand color: one confident, saturated color used for primary
    actions (Add to Cart, Buy Now, primary buttons, active nav states,
    links). Suggested direction: a deep, trustworthy blue or a warm forest
    green — pick ONE and use it everywhere consistently. Do not use more
    than one "primary" hue across the app.
  - Neutral scale: a full gray scale (near-white background, light gray
    panel backgrounds, mid gray borders/dividers, dark gray/near-black body
    text). Avoid pure #000000 text — use a dark neutral (e.g. slate-900/
    gray-900 equivalent) for better feel.
  - Semantic colors: 
      success/in-stock = green, 
      warning/low-stock = amber, 
      error/out-of-stock/destructive = red, 
      sale/discount badge = a distinct accent (e.g. red or orange) used only
      for price-drop indicators so it stays meaningful.
  - Backgrounds: alternate very subtle neutral tones (white vs. very light
    gray, e.g. gray-50) between sections to create rhythm without using
    hard borders everywhere.

3.2 Typography
  - One primary sans-serif font family for everything (body + headings) —
    if the project already loads a font, keep it; otherwise use a clean
    system/Tailwind default stack (e.g. Inter-like).
  - Clear scale: page titles largest and boldest (e.g. text-3xl/4xl,
    font-bold), section headings (text-xl/2xl, font-semibold), card/product
    titles (text-base/lg, font-medium), body/description text (text-sm/base,
    font-normal, comfortable line-height), meta/secondary text (text-xs/sm,
    lighter gray).
  - Prices should visually stand out: bolder weight, primary or near-black
    color; a struck-through original price next to a discounted price
    should use a lighter/muted gray with line-through.

3.3 Shape language
  - Cards and panels: consistent rounded corners across the whole app (pick
    one radius scale, e.g. "rounded-lg" for cards, "rounded-md" for inputs/
    buttons/badges — don't mix radius sizes randomly between components).
  - Elevation: subtle shadows for cards that sit on a page (e.g. a soft
    shadow-sm at rest, slightly deeper shadow-md on hover for interactive
    cards like product cards). Avoid heavy/dark drop shadows.
  - Borders: thin, light neutral borders (1px, light gray) used sparingly to
    separate content — prefer subtle background-color shifts or spacing
    over harsh borders where possible.
  - Buttons: clearly differentiated primary (filled, brand color, white
    text), secondary (outlined or light-gray filled, dark text), and
    destructive/danger (red) styles. Consistent height/padding across all
    buttons of the same size tier. Visible hover and focus states on every
    interactive element (hover: slightly darker/lighter shade; focus:
    visible ring for accessibility).
  - Product cards: image area with consistent aspect ratio across the grid,
    product name, price (and discounted price if applicable), a small
    rating/stock indicator if data exists, and a clear add-to-cart action —
    all with consistent internal padding and spacing so the whole grid
    feels uniform.

3.4 Spacing & rhythm
  - Use a consistent spacing scale (Tailwind's default scale is fine) for
    padding/margin/gaps — don't hand-pick arbitrary pixel values.
  - Generous whitespace around major sections; tighter, consistent spacing
    within a single component (e.g. inside a product card).
  - Page content should sit within a consistent max-width container with
    consistent horizontal padding on mobile vs desktop.

3.5 Responsiveness
  - Every restyled component/page must look correct at mobile (base),
    tablet (sm/md), and desktop (lg/xl) breakpoints. Product grids should
    reflow (e.g. 1 column mobile → 2–3 tablet → 4+ desktop) using Tailwind's
    responsive grid utilities.
  - Navbar must collapse into a mobile-friendly pattern (hamburger/menu)
    without changing any existing navigation logic — only its presentation.

3.6 Motion & feedback (subtle, not flashy)
  - Light, quick transitions on hover/focus/state changes (e.g.
    transition-colors, transition-shadow, 150–200ms) — never long or
    bouncy animations.
  - Loading states: skeleton placeholders or a simple, on-brand spinner —
    not a generic browser default.
  - Empty states (empty cart, no search results, no orders yet): friendly,
    on-brand illustration/icon + short message + a clear next action button
    — not just blank space or a plain "No data" text.

3.7 Accessibility
  - Maintain sufficient color contrast for text on backgrounds (avoid light
    gray text on white for anything important).
  - Keep all existing aria-*, alt text, and semantic HTML elements intact
    or improve them — never remove them.
  - Ensure focus states remain visible on all interactive elements after
    restyling.


3.8 Component specifications — be explicit, don't improvise per-component
-----------------------------------------------------------------------
Every instance of the same component type must look identical across the
whole app. Don't restyle the "Login" button differently from the
"Checkout" button — build one button system and reuse it everywhere.

BUTTONS
  - Sizes: at minimum a default size and a small size (e.g. for compact
    areas like cart line-item quantity controls). Consistent height and
    horizontal padding within each size across the whole app.
  - Variants:
      Primary — filled, brand color background, white text, used for the
        single main action on a screen (Add to Cart, Place Order, Sign In).
      Secondary — outlined or light-gray filled, dark text, used for
        lower-priority actions (Cancel, Continue Shopping, View Details).
      Destructive — red, used only for irreversible/negative actions
        (Remove from Cart, Delete Account, Cancel Order).
      Ghost/text — no background, brand-color or gray text, used for
        tertiary actions inside dense areas (e.g. "Edit" links in a table).
  - States: default, hover (slightly darker/lighter shade), active/pressed
    (slightly darker still), focus (visible ring outline, do not remove
    for keyboard users), disabled (reduced opacity, no pointer cursor,
    no hover effect).
  - Icon buttons (cart icon, wishlist heart, close "x"): consistent
    circular or square tap target size (comfortable for touch, not
    cramped), same hover/focus treatment as text buttons.
  - Loading state: when a button triggers an async action already in the
    code (e.g. "Add to Cart" while the request is in flight), style its
    existing loading/disabled state clearly (spinner + dimmed) rather than
    leaving it looking identical to the idle state — but do NOT add new
    loading state logic if none exists; only style what's already there.

INPUTS / FORMS
  - Text inputs, email, password, number, textarea: consistent height
    (textarea taller, same width behavior), consistent padding, light
    neutral border at rest, border shifts to primary brand color + subtle
    ring/glow on focus, rounded corners matching the app's radius scale.
  - Labels: placed above the input (not just relying on placeholder text),
    small/medium weight, neutral-dark color. Required fields marked with a
    small asterisk or "(required)" label, styled subtly, not alarming.
  - Placeholder text: lighter gray than real input text, so users never
    confuse placeholder content with an actual filled value.
  - Validation/error state: red border + small red helper text below the
    field explaining the error, only rendered when the existing logic
    already flags an error — do not invent new validation logic, only
    style the existing error state cleanly if one exists in the code.
  - Success/valid state (if the code already has one, e.g. a checkmark
    after a valid email): small green accent, subtle, not oversized.
  - Checkboxes and radio buttons: custom-styled to match the brand (not
    raw browser defaults), clear checked vs unchecked states, adequate
    spacing from their label text, comfortable click/tap target including
    the label itself.
  - Select/dropdown inputs: same border/radius/focus treatment as text
    inputs, a clear custom chevron icon, consistent option list styling
    (hover highlight, selected item indicator) if the dropdown is a custom
    component rather than a native <select>.
  - Search bars: rounded pill or rounded-rect shape (pick one and use it
    everywhere search appears), search icon inside the field, clear "x" to
    reset when text is present if that logic already exists.
  - Quantity steppers (cart, product detail): compact [–][number][+]
    control, consistent button sizing on both sides, disabled state on the
    minus button when quantity is at its existing minimum (style only,
    don't add new min/max logic if none exists).
  - Form layout: consistent vertical spacing between fields, grouped
    logically (e.g. shipping fields together, payment fields together)
    using spacing/dividers rather than heavy borders.

BADGES / TAGS
  - Sale/discount badge: small, high-contrast accent color (e.g. red or
    orange), rounded, positioned consistently on every product card
    (e.g. top-left corner of the image).
  - Stock status badge: green "In Stock", amber "Low Stock", red "Out of
    Stock" — same shape/size/position pattern as the sale badge, only
    color changes.
  - Category/new-arrival tags: neutral or brand-tinted, smaller and less
    visually loud than the sale badge so the sale badge stays the clear
    priority signal.

CARDS / PANELS
  - One consistent card style (radius, shadow, padding, border) reused for
    product cards, order summary cards, account info panels, and any other
    "boxed" content — don't let different sections invent their own card
    look.
  - Hover behavior on interactive cards (e.g. product cards): subtle lift
    (slightly deeper shadow and/or a 1–2px translate-up), fast transition.

MODALS / DIALOGS
  - Centered, dimmed/blurred backdrop, consistent max-width, consistent
    corner radius and padding, a clearly visible close "x" in a consistent
    corner, primary action button bottom-right, secondary/cancel button
    to its left — reuse this same pattern for every modal in the app
    (confirm-delete, quick-view, image zoom, etc.) if modals already exist.

TOASTS / ALERTS / INLINE NOTICES
  - Success (green), error (red), warning (amber), info (neutral/blue) —
    consistent left-accent-bar or icon + background tint pattern, same
    corner radius and padding as other components, same position on
    screen every time it's used (only style existing toast/alert logic,
    don't add a new notification system).

NAVIGATION AIDS
  - Breadcrumbs (e.g. Home / Category / Product): small text, muted gray
    with the current page in darker/bold, separated by a simple "/" or
    chevron icon.
  - Pagination: consistent button/number sizing, clear active-page
    indicator (filled or underlined in brand color), disabled state for
    prev/next at the start/end of the list.
  - Tabs (e.g. account page sections, product detail "Description /
    Reviews / Shipping"): underline or pill style — pick one and use it
    everywhere tabs appear, clear active vs inactive state.

RATINGS
  - Star rating display: consistent star size and spacing wherever it
    appears (product card, product detail, reviews list), filled stars in
    a warm accent color (e.g. amber/gold), empty stars in light gray —
    only style existing rating data, don't invent new rating logic.

EMPTY / ERROR / 404 STATES
  - Centered content: simple icon or illustration placeholder, short bold
    heading, one line of supporting gray text, one clear action button
    (e.g. "Browse Products" on an empty cart) — consistent pattern reused
    for empty cart, empty search results, empty order history, and the
    404 page.


3.9 Dark mode — single token system, used everywhere, no exceptions
-----------------------------------------------------------------------
This app supports both light and dark mode. Every single color-bearing
className must include a `dark:` counterpart. Use Tailwind's class-based
dark mode (`dark` class on a parent, typically <html> or <body> — check
tailwind.config.js for `darkMode: 'class'`; if it isn't set to class-based
dark mode yet, set it, since that's a config change needed to support the
existing toggle logic, not a logic change to a component).

Define and reuse these exact token pairs everywhere a color is needed —
do not invent new colors per component:

  Page background:        bg-white               dark:bg-gray-950
  Section/alt background: bg-gray-50              dark:bg-gray-900
  Header background:      bg-white                dark:bg-gray-950
  Sidebar background:     bg-white                dark:bg-gray-900
  Card/panel background:  bg-white                dark:bg-gray-900
  Border (default):       border-gray-200         dark:border-gray-800
  Border (subtle):        border-gray-100         dark:border-gray-800/60
  Body text:               text-gray-900          dark:text-gray-100
  Secondary/meta text:    text-gray-500           dark:text-gray-400
  Placeholder text:       text-gray-400           dark:text-gray-500
  Primary brand color:    [pick ONE, e.g. blue-600]  dark:[same hue,
                           e.g. blue-500 — one step lighter for contrast
                           on dark backgrounds]
  Primary hover:          [primary + one shade darker]  dark:[primary +
                           one shade lighter than the dark base]

The Header, both Sidebars (user + admin), the Footer, and every Card must
all pull from this exact same background/text/border token set. If the
Header is `bg-white dark:bg-gray-950`, the user panel's cards and sidebar
must NOT independently end up on a different, unrelated color — they use
the SAME tokens above, so light mode stays visually consistent and dark
mode stays visually consistent, across every page.

Before starting Phase 1 in Section 5, add these tokens to tailwind.config.js
under theme.extend.colors if useful (e.g. a `brand` color key), so every
component can reference `bg-brand-600 dark:bg-brand-500` etc. consistently
instead of repeating raw Tailwind grays everywhere. This is a config
addition, not a logic change, and is allowed.


3.10 Icon usage discipline
-----------------------------------------------------------------------
Icons are a tool for clarity, not decoration. Only add an icon to an
element in these cases:
  - It replaces or reinforces a common, universally recognized action:
    cart, search, user/account, close (x), menu (hamburger), chevron for
    dropdowns/accordions/pagination, star for ratings, trash for delete,
    edit/pencil for edit actions, checkmark for success/confirmation.
  - It already existed in the component before your edit.
  - This brief explicitly calls for one (e.g. search icon in a search bar,
    quantity stepper +/-, breadcrumb separator chevron).
Do NOT add icons next to: form field labels, plain body text, section
headings, navigation text links, or buttons that already have clear text
(e.g. don't add a random icon in front of "View Details" or "Continue
Shopping" unless one is specified above). If you're unsure whether an
icon belongs somewhere, leave it out — the default is no icon.

If icons are needed and the project already has an icon library installed
(check package.json — e.g. lucide-react, react-icons, heroicons), use
that existing library consistently. Do not install a new icon library.


3.11 Sidebar & panel layout spec (User Panel + Admin Panel)
-----------------------------------------------------------------------
Both `UserPanelSidebar.jsx` (used within the user-facing panel, likely via
`User.jsx`/`Layout.jsx`) and the sidebar inside `AdminLayout.jsx` must
follow this exact same structural pattern — they are two instances of one
design, not two different designs:

  - Fixed width on desktop (e.g. w-64), collapsible/hidden behind a menu
    toggle on mobile — do not let the sidebar squeeze the main content
    into an unreadable width on small screens.
  - Sidebar background and border use the Sidebar background token from
    Section 3.9, with a right-side border (border-r) separating it from
    main content, using the Border (default) token.
  - Nav items: full-width clickable rows, consistent vertical padding,
    left-aligned icon (if the item already has one) + label, rounded
    corners on the row itself (not the whole list), consistent gap between
    icon and label.
  - Active/current nav item: filled background using a light tint of the
    primary brand color (or brand color at low opacity) with the primary
    brand color text, in both light and dark mode — this is the ONE clear
    visual signal for "you are here," don't rely on font-weight alone.
  - Inactive nav items: default text color, transparent background, with
    a subtle hover background (light gray / dark gray tint) and text
    color shifting toward the primary brand color on hover.
  - Section grouping (if the sidebar has grouped links, e.g. "Account" /
    "Orders" / admin's "Products" / "Orders" / "Users" / "Announcements"):
    small, uppercase, muted-gray section labels above each group, with
    consistent spacing between groups.
  - The admin sidebar and user sidebar may differ in WHICH links they
    show (that's existing logic/data, untouched) but must be visually
    indistinguishable in terms of spacing, radius, active-state styling,
    and color tokens used.


3.12 Product card / list item — required internal order
-----------------------------------------------------------------------
Every component that renders a single product as a card, tile, or list
row (ProductCard.jsx, GroupCard.jsx, GroupTile.jsx, GroupPreview.jsx,
CategoryCard.jsx, CategoryTile.jsx, CategoryPreview.jsx, ViewAllTile.jsx,
and any inline product rendering inside AllProducts.jsx, Products.jsx,
Product.jsx, GroupProductsPage.jsx, CategoryGroupsPage.jsx,
AllGroupsPage.jsx, AllCategoriesPage.jsx) must present its content in this
exact top-to-bottom (or, for a horizontal row layout, left-to-right)
order — do not reorder this per component:

  1. Image first — consistent aspect ratio across every card in the same
     grid, image fills its container (object-cover), rounded top corners
     matching the card's radius if the image is flush with the card edge.
     Sale/stock badges (Section 3.8) are the only things allowed to
     overlay on top of the image itself.
  2. Title/name — directly below the image, clear card-title typography
     weight from Section 3.2, truncated with ellipsis after 1–2 lines if
     long (don't let long titles break the grid's row height).
  3. Short description/meta (if the component already renders one) —
     smaller, muted text, directly below the title, truncated similarly.
  4. Rating (if the component already renders one) — below description,
     using the star rating spec from Section 3.8.
  5. Price (and struck-through original price if there's a discount) —
     below rating, using the price typography from Section 3.2.
  6. Action row last — Add to Cart / View button and any icon actions
     (wishlist heart, quick view), at the bottom of the card, using the
     button spec from Section 3.8.

Only render the pieces (2–6) that the component already renders based on
its existing data/props — do not add new fields. This rule governs ORDER
and SPACING of whatever the component already shows, not what data it
shows.
